# ZanSQL Lab Log — Entry 00
## Why databases don't store one row per file

**Date:** 2026-09-25
**Stage:** 0 — data on disk, before any page/B+tree design
**Environment:** Linux (ext4), g++, C++17

---

## Question

If we store each row of a table as its own file, what does it cost us —
in disk space and in read speed — compared to packing many rows into
one file?

## Setup

Two versions of the same 1000 rows (`"row number N"`), generated by a
single C++ program (`experiment1.cpp`):

- **Version A** — one file per row: `many_files/row_1.txt` ... `row_1000.txt`
- **Version B** — one file, all rows appended in sequence: `packed.txt`

Measured with:
- `du -sb` — apparent size (real byte count of content)
- `du -sh` — actual disk usage (blocks allocated by the filesystem)
- `std::chrono::steady_clock` in a second program (`experiment2.cpp`), timing
  a full read-back of each version

## Results

### Space

| | Content (bytes) | Disk used (bytes) | Waste ratio |
|---|---|---|---|
| Version A (1000 files) | 39,469 | 4,194,304 (4.0M) | **≈106×** |
| Version B (1 file) | 14,893 | 16,384 (16K) | **≈1.1×** |

### Speed (reading all 1000 rows back)

| | Time |
|---|---|
| Version A (1000 files) | 268,006 µs (≈268 ms) |
| Version B (1 file) | 610 µs (≈0.6 ms) |

**≈439× slower** for the one-file-per-row version.

## Why

**Space:** filesystems allocate storage in fixed-size blocks (4096 bytes on
this ext4 filesystem — confirmed earlier via `stat` on a single 13-byte
file, which showed `Blocks: 8` × 512-byte units = 4096). A file smaller
than one block still consumes a full block. 1000 tiny files each round
up to ~4096 bytes, regardless of real content size. A single packed file
only wastes space in its *last, partial* block.

**Speed:** each `open()`/`close()` on a file carries roughly fixed OS
overhead — directory lookup, permission check, inode resolution, file
descriptor setup/teardown — independent of how little data the file
holds. 1000 files means paying that fixed cost 1000 times. One file
pays it once, then streams bytes continuously.

## Conclusion

The cost of "one row = one file" is not about the data itself, it's
about the number of separate OS-level operations and allocations. Both
the space waste and the speed cost come from the same root cause:
**small, separate units of work are expensive; fewer, larger ones are
cheap.**

This is the reason real storage engines (InnoDB, SQLite, etc.) never
map rows to individual files. Instead they keep one (or a few) files
per table and pack many rows into fixed-size chunks they manage
internally — **pages** — reading and writing in page-sized units rather
than row-sized ones.

## Next

Design a page format: a fixed-size chunk (e.g. 4096 bytes) that holds
many packed rows, plus enough bookkeeping to find, insert, and later
delete a specific row inside it without reading the whole file.
